# Documentation Principles

PALM documentation is written for hobbyists and engineers who want to understand and use the system without wading through formal project language.

## Write naturally

Use the words people would use while working with plants, tools, parts, boxes, shelves and devices.

Prefer:

- move a plant
- put a component in a box
- print a label
- scan a pot

Avoid replacing simple ideas with enterprise language unless a precise technical term is needed.

## Work from the top down

Start with the main idea, then add the detail needed to support it.

A document should normally move through:

1. purpose
2. concepts
3. design
4. implementation detail

Do not make the reader discover the point at the end.

## Say it once

Put each idea where it belongs and explain it clearly there.

Other documents should refer to it rather than repeat the same introduction, reasoning, summary and conclusion.

## Give each document one job

A document should answer one main question.

Examples:

- the README explains why the repository exists
- the architecture overview explains the shape of the system
- the device architecture explains how small devices take part
- a use case explains one piece of real work

## Keep the history useful

Early documents are working documents. They capture the thinking while it is fresh and are refined as the design develops.

The aim is not to make every first draft look finished. The aim is to avoid losing useful ideas and decisions.

## Separate engineering and user guidance

Engineering documents explain the model, architecture and implementation.

Family guidance will explain how to use PALM in simple task-based terms, such as adding a plant, moving a box or printing a replacement label.

The two sets of documents serve different readers and should not be mixed.
